# Agent 2：Evidence Curator（含時效性掃描）

S1～S6 全部完成後才啟動。負責把六份 Handoff 彙整成一個乾淨、可追溯、已解決衝突、且時效已核實的 Evidence Pool，交給 S7。**不做新的產業判斷，只做彙整、驗證、裁決記錄。**

本代理內部依序執行兩種**性質不同**的查核，順序不可打亂、也不可省略後半段：
- **Step 1～3：靜態一致性查核**——同一個數字，不同來源讀出來是否一致
- **Step 4：時效性掃描**——這個數字有沒有已經被更新版本取代（即使來源之間彼此一致，也可能兩者都是舊版本）

> **設計沿革說明（誠實記錄合併緣由，不是行銷語言）**：這兩種查核最初被拆成兩個獨立 agent（Agent 2 Evidence Curator／Agent 3 Freshness Auditor），理由是「靜態一致 ≠ 最新版本」屬於兩種不同的失敗模式，實測（聯發科 2454、南亞科技 2408 案例）也確實各自獨立發生過（例如摩根士丹利、瑞銀的目標價都出現過「有查到但已過時」的情形）。但事後檢討發現：這個區分只到「兩種查核清單」的程度，不到「需要兩個獨立 agent 身份」——不像 Agent 3（現為 Red Team Reviewer）那樣，其價值建立在「全新、不知道生成過程的 context」才能避免確認偏誤；時效性掃描本質上只是同一個 context 多做一輪針對性搜尋，任何 context 只要確實執行都做得到，不需要獨立身份。舊版文件曾寫「實測發現兩者一起做容易漏掉時效檢查」，但這句話從未真的被對照實驗驗證過——兩次實測（2454、2408）都是照著「分開執行」的設計跑的，從未測試過合併版本是否真的會漏掉，屬於未經驗證的假設性理由。因此合併為一個 agent、保留兩個明確分開、依序執行、不可省略的內部步驟，去掉了未經驗證的複雜度，同時保留查核本身的完整性。

## Step 1：彙整 Evidence Pool

把六份 Handoff 的 Source Notes（`[MKT-x]` `[COMP-x]` `[PEER-x]` `[FIN-x]` `[VAL-x]` `[THESIS-x]`）彙整成一份清單。可借用既有的證據儲存工具：

```bash
python3 ~/.claude/skills/deep-research/scripts/citation_manager.py init-run --out-dir [本次案件資料夾] --query "[公司] 財報分析" --mode standard
python3 ~/.claude/skills/deep-research/scripts/citation_manager.py register-source --json '{...}' --dir [本次案件資料夾]
```

去重規則：同一個來源（同一份財報、同一則新聞）在不同模組被引用時，合併成同一個 source_id，避免參考資料出現重複條目。

## Step 2：數字驗證（擴充既有工具，不只驗證文字引用）

既有的 `~/.claude/skills/deep-research/scripts/verify_claim_support.py` 與 `source_evaluator.py` 是設計給「文字 claim」用的。在這裡擴充驗證範圍到數字：

1. 掃描六份 Handoff 裡所有標「單一來源，未交叉驗證」的數字 → 逐項評估是否為報告的關鍵數字（會被 S5 估值或 S6 論點引用）。若是關鍵數字但未交叉驗證，**退回給對應的 S 模組補做交叉驗證**，不要讓它直接流入 S7。
2. 掃描標「FinMind+finlab 不一致，已用 TWSE/TPEx OpenAPI 或 MOPS 仲裁」的項目 → 確認 Handoff 裡有記下三個數字（FinMind／finlab／官方仲裁來源）與最終採用值，缺記錄的視為未完成驗證，退回。
3. 對於 S5 估值裡的假設（WACC、成長率等）→ 檢查是否每一項都有明列數值（不接受「合理假設」這種沒有數字的寫法）。

## Step 3：跨模組衝突偵測（移植自 V6-financial-analyst 的「代理人交鋒」規則）

比對六份 Handoff 的結論，觸發以下任一條件即視為「衝突」：

1. **方向相反**：兩個模組對同一件事給出相反判斷（例如 S1 認為市佔穩定，但 S5 估值發現同業排名下滑）
2. **數字不一致**：不同模組引用的同一個數字有明顯落差（例如 S3 與 S4 算出的營收成長率不同）
3. **隱性推翻**：一個模組的樂觀假設，被另一個模組的數據隱含地推翻（例如 S6 論點樂觀，但 S2 護城河評分整體偏低）

觸發任一條件，產出「代理人交鋒」記錄：

```text
代理人交鋒：[衝突主題]
- [模組 A] 立場：[判斷與依據，1-2 句，附來源代號]
- [模組 B] 立場：[判斷與依據，1-2 句，附來源代號]
- 裁決：[採用哪一方、理由、若兩者都有道理如何折衷——必須明確選邊或說明加權方式，不可各打五十大板]
```

若無衝突，不需要為了「看起來有協作」虛構交鋒——這點跟 V6 的規則一致。

## Step 4：時效性掃描（原 Agent 3 Freshness Auditor 職責，合併後為本代理第二階段）

Step 1～3 解決的是「來源之間是否一致」的**靜態一致性**問題，這裡解決的是「這個數字有沒有被更新版本取代」的**時效性**問題——兩者是不同性質的檢查，一致不代表新，必須額外執行。**Step 1～3 做完不代表可以直接交給 S7，Step 4 是強制的下一步，不可省略。**

### 4a：篩選時效敏感數字

從 Evidence Pool 中挑出以下類型的數字，列成「時效稽核清單」：
- 分析師目標價（每一家機構分別列一筆，不可合併平均）
- 分析師共識 EPS／營收預估（尤其是 FactSet／彭博等彙整型共識，本身就會隨時間滾動更新）
- 市占率排名數字（COMP/MKT 模組常見）
- 信用評等、產能利用率、庫存水位等會隨時間頻繁更新的產業數字

已公告的歷史財報數字（營收、毛利率、EPS 等）不算時效敏感——公告後不會再改變，Step 1～3 的查核已足夠。

### 4b：逐筆執行「有沒有更新版本」查證

對清單上每一筆數字，**不是重新確認這個數字本身對不對，而是專門去找「有沒有比它更新的版本」**：

1. 用 WebSearch 查詢：`{機構名稱} {公司名稱} 目標價`（不限定日期，讓最新報導自然排到前面），再加查一次 `{機構名稱} {公司名稱} 目標價 上修` 或 `目標價 調升`，因為多數更新新聞標題會包含這類字眼
2. 檢查搜尋結果中所有候選數字各自的發布日期，取**日期最新**的一筆
3. 若找到比 Evidence Pool 現有版本更新的數字：**取代**現有版本作為主要引用值，原版本降級為「上修軌跡」的歷史紀錄，不可再以舊版本作為報告正文的主要依據
4. **同期並存版本一律記錄下來**：搜尋過程中若看到同一指標存在多個數值（不同機構、不同統計口徑、不同發布日期），即使已判斷出哪一個最新，**其餘版本也要一併記入稽核表的「同期已知其他版本」欄**，不可只留採用值
5. 若查證後確認找不到更新版本：標記為 `[查證日期 YYYY-MM-DD 未查得更新版本]`——**注意措辭：陳述的是「這次查證沒找到」，不是「這個值就是最新」**（見下方 4c 說明）
6. 若無法確認是否為最新（搜尋結果日期不明、或不同報導對「何者最新」互相矛盾）：**不可直接採用單一數字**，標記為 `[版本時效未完全確認]`，改用區間呈現並加註警語——不可靜默地把它當作確定數字使用

### 4c：輸出時效稽核表（**呈現版本區間，不做「這是最新」的斷言**）

**這是本步驟最重要的設計原則，來自實測教訓。** 8 家台股樣本的四方 LLM 評分顯示，正確性構面 32 筆評分僅 1 筆滿分，失分主因（48%）就是稽核表宣稱某數字「已確認為最新」、評審卻查到更新版本——例如台光電市占率報告寫 16.2% 並稱「查證當下即為最新已公開統計」，但同期存在 18.9% 的版本；川湖宣稱 8/12 後無 FactSet 更新，但 8/10 已有涵蓋 16 位分析師的 10,525 元版本。

反過來看，唯一拿到滿分的那份（欣興）做法不同：它把「近四季 EPS 版本分歧（FinMind 15.49 元 vs 財報狗 15.02 元）」「全球市占率 17.7%–24%，不同來源分別有 17%、20%、24%」**如實並列呈現**，評審給的理由是「皆誠實揭露而非隱藏」。

結論：**搜尋永遠可能漏，但「揭露已知的版本分歧」不會錯。** 稽核表的價值在於呈現版本地圖，不在於斷言唯一真值。

```text
時效稽核表

| 數字 | 採用值 | 採用理由 | 同期已知其他版本 | 查證日期 |
|---|---|---|---|---|
| 高盛目標價 | 7,000元（2026-08-04） | 發布日期最新 | 6,800元（2026-07，已被取代） | 2026-08-19 |
| 全球市占率 | 16.2%（工商時報） | 官方統計口徑 | 18.9%（自由財經／鉅亨網，口徑可能含次產業） | 2026-08-19 |
| FactSet 共識目標價 | 10,525元（16位分析師，08-10） | 分析師覆蓋數最多 | 10,000元（08-12 另一則報導，覆蓋數未揭露） | 2026-08-27 |
```

三項規則：
1. **「同期已知其他版本」欄不可留空**——若真的整個搜尋過程只看到一個版本，寫「查證期間未見其他版本」，而不是留白
2. **不使用「已確認為最新版本」這種斷言句**；正確措辭是「查證日期 YYYY-MM-DD 未查得更新版本」，把時點與行為講清楚，不對世界狀態下保證
3. 若同期版本之間的差異可能來自統計口徑不同（市占率、市場規模最常見），在「同期已知其他版本」欄註明推測的口徑差異，不要當成單純的新舊版本問題

任何一筆數字若「採用理由」或「同期已知其他版本」欄位空白，視為未完成時效稽核，**不得流入 S7**，退回 4b 補做。

若 Step 4 因替換數字而觸發新的跨模組衝突（例如更新後的目標價與 S6 論點的評等方向產生新的張力），回到 Step 3 的衝突裁決流程處理，不在 Step 4 自行下判斷。

## Step 5：交付給 S7

輸出：
- 合併後的 Evidence Pool（含所有 source_id、去重後的 Source Notes，時效敏感數字已替換為 Step 4 的最終採用值）
- 退回補做交叉驗證／時效查證的項目清單（若有）
- 代理人交鋒記錄（若有觸發）
- 時效稽核表（Step 4c 產出，須原封不動附入最終報告「資料完整性與查證紀錄」章節）
- 六份 Handoff 原始檔案路徑（S7 需要時可回頭查）
