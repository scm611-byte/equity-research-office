# S7：Synthesis / Report

輸入：Agent 2 Evidence Curator 交出的合併 Evidence Pool（已完成靜態一致性查核與時效稽核，含衝突裁決記錄與時效稽核表）。這是整個流程裡**唯一**允許寫完整敘事報告的階段。

## Step 1：漸進式寫檔（移植自 deep-research skill 的 report-assembly.md）

不要一次生成整篇報告。用 Write/Edit 逐段寫入檔案，**每次呼叫 ≤5,000 字**（原為 2,000 字，實測 8 家樣本後放寬：最長報告 26,000 字元在 2,000 字粒度下需 13 次以上寫檔呼叫，固定開銷偏高；5,000 字粒度可將呼叫次數減半，且仍在單次回應輸出長度的安全範圍內）：

1. 建立資料夾：使用者當前工作目錄下的 `outputs/{公司}_{代號}_{YYYYMMDD}/`
2. 依 `templates/final_report_template.md` 骨架，依序：評等摘要 → 執行摘要 → 公司概況 → 市場與產業展望（來自 S1）→ 競爭地位（S2）→ 同業比較（S3）→ 財務分析（S4）→ 估值分析（S5）→ 投資論點（S6，含代理人交鋒裁決結果）→ 主要風險 → 資料缺口與限制（含所有「未交叉驗證」項目）→ 參考資料
3. 每寫完一段，追記引用來源（沿用 Evidence Pool 的 source_id，最後統一編號）

## Step 2：字數上限處理（**已移除自動續寫機制**）

**設計變更紀錄（2026-09，8 家台股樣本實測後）**：本步驟原為「累計超過 18,000 字時，存狀態檔並 spawn 新 agent 接續寫作」，現已移除，理由如下：

- **從未合法觸發**：8 份 Deep 模式報告字數為 8,852～15,357 字，最長者距 18,000 門檻仍差 2,643 字，觸發次數 0/8。這並非巧合——Deep 模式的目標字數本就設定為 8,000–15,000 字，門檻設在目標區間**上方**，等於這個機制的觸發條件是設計上刻意不該達到的狀態。
- **反而製造過事故**：唯一一次作動出現在奇鋐的失敗版本，報告在 13,529 字元（遠低於門檻）處留下 `<!-- CONTINUE-5 -->` 標記後中斷。當時真正原因是執行額度耗盡，agent 把續寫標記當成「我快沒資源了」的逃生口使用，產出一份無法使用的殘缺報告。
- **維護成本不成比例**：狀態檔設計、spawn 新 agent、讀檔接續、清理狀態檔，光參考文件即 167 行，換來一個從未合法觸發卻已造成一次事故的功能。

**現行規則**：S7 若寫到接近 18,000 字，代表 S1～S6 的字數預算失控（Deep 模式 S1+S2+S3 上限 1,800 字、S4+S5+S6 上限 2,200 字），應**退回檢查各階段 Handoff 是否超出預算**，而不是啟動續寫接力。任何情況下都不得使用 `<!-- CONTINUE -->` 之類的標記中斷交付，也不得用「...(內容過長省略)」等佔位符省略章節。

## Step 2.5：資料完整性與查證紀錄（Data Integrity & Verification Log，實測後新增的必要章節）

這是跟單一提示詞生成的報告拉開差距最有感的一段，**必須寫進最終報告**，不是選配。內容包含：
1. 過程中攔截到的任何離譜數字（例如欄位誤用算出不合理的 ROE），寫出「錯在哪、怎麼發現、怎麼修正」
2. 任何資料分歧的揭露（本益比、資本支出等），不要只在資料缺口與限制提一句，要在這裡完整說明
3. 如果有機會跟其他獨立來源（例如另一份分析報告、另一個資料集）的數字做比對，把吻合或不吻合的結果寫出來——**吻合本身就是有價值的交叉驗證證據，不是「反正一樣就不用提」**
4. 統計一下正文引用數（[1]~[N]）與參考資料條目數是否一致，寫成一句可追溯率的總結
5. **Agent 2 Evidence Curator 產出的時效稽核表**（Step 4 時效性掃描的產出），原封不動附入，不得省略或僅摘要（見 reference/evidence-curator.md Step 4）
6. **Agent 3 Red Team Reviewer 產出的紅隊挑戰清單**（表格化摘要，見 Step 2.6 格式規定）
7. **「結論影響追蹤」兩行對照**——**本子節已自「投資論點」章節移至此處**（2026-09 變更，見下方說明）

> **變更說明：為何把「結論影響追蹤」移出投資論點正文。** 實測發現，即使已把「跨模組交叉檢驗」等系統內部用詞改成中性措辭，這個子節的**呈現形式本身**仍被評審判定為流程痕跡：Claude 評審對奇鋐的評語是「以『單獨判斷 vs 綜合全部分析構面後之最終判斷』的方式呈現內部推理過程，讀起來略帶審閱式的自我對話色彩，打斷了原本應一氣呵成的投資論證」；Gemini 對川湖亦有類似評語。問題不在用詞，在於「展示自己如何從 A 想到 B」這件事寫在讀者要看的論證段落裡，本質上就是工作稿語氣。移到查證紀錄章節後，揭露完整度不變，只是換了位置——投資論點正文只呈現最終判斷與其分析理由。

## Step 2.6：Agent 3 — Red Team Review（初稿完成後、進入 Step 3 品質把關前執行）

完整機制見 `reference/red-team-agent.md`。摘要：
1. 初稿（含 Step 2.5 前四點）寫完後，用 Task 工具 spawn 一個全新 context 的 agent，只給它「初稿全文＋Evidence Pool（含時效稽核表）」，不給生成過程
2. 該 agent 依四類攻擊框架（反向論證測試／未解釋矛盾掃描／過度自信主張掃描／情境測試）輸出「紅隊挑戰清單」
3. 收到清單後逐項回應：挑戰成立 → 修改報告內容（含視情況調整評等或目標價區間）；不成立 → 在報告對應章節加明確反駁與理由；**不可略過任何一項、不可只在內部處理不呈現給讀者**。修改時**只寫改後的分析結論，不要把複核過程本身寫進正文**（例如不要寫「經Red Team複核後…」）——複核過程留給「資料完整性與查證紀錄」章節，正文讀起來要像乾淨定稿，不是工作稿；詳細示範見 `reference/red-team-agent.md`「修改時的寫作規範」一節
4. 把挑戰清單（含處理結果）補進 Step 2.5 的「資料完整性與查證紀錄」章節後，才進入 Step 3 品質把關

## Step 3：品質把關（融合 financial-research-lite 的 S7 checklist + deep-research 的 quality-gates.md）

逐項確認，任一項不過退回修正：
- [ ] 每個重要數字都有來源標註或明確揭露為估計值
- [ ] Historical／Estimate／Guidance／Consensus 四類數據明確區分，不混用
- [ ] 投資論點與評等跟 S1～S6 的證據一致（若 Evidence Curator 有交鋒裁決，最終評等要反映裁決結果）
- [ ] Market 與 Financial 章節沒有重複內容
- [ ] 估值假設全部明列（WACC、成長率、終值成長率）
- [ ] 「結論影響追蹤」兩行**寫在「資料完整性與查證紀錄」章節內**（2026-09 起自投資論點移出，見 Step 2.5 變更說明），不得留在投資論點正文。內容為：
  - 若僅依單一分析構面（例如估值或成長動能）單獨判斷，可能得出的結論
  - 綜合本報告全部分析構面後之最終判斷，若與單一構面判斷相同也要寫「結論未變，因為：[理由]」，不可省略
  - 兩行皆不得出現「S5」「模組」「交鋒裁決」等系統內部用詞，改用「估值分析」等讀者看得懂的說法
- [ ] 時效敏感數字（分析師目標價、共識 EPS、市占率等）是否都走過 Agent 2 Evidence Curator 的 Step 4 時效性掃描，時效稽核表是否已附入「資料完整性與查證紀錄」章節；正文是否還殘留任何被稽核表標記為非最新版本的舊數字
- [ ] Agent 3 Red Team Reviewer 的挑戰清單是否已附入「資料完整性與查證紀錄」章節，且每一項都有明確處理結果（採納修改／反駁及理由），不可只有清單沒有處理結果。**已知失敗模式（2330 案例第三批財報，2026-08）**：曾出現標題寫著「### 紅隊挑戰清單」、底下卻只接一句「（待Agent 3獨立審查完成後填入...）」的空殼版本直接交卷，執行摘要還照樣寫「已綜合紅隊複核結果」——標題字串本身沒有缺，容易被粗略檢查誤判為完成。`validate_equity_report.py` 已強化為檢查標題後的內文長度與結構（是否有「挑戰1」或「未發現需列入挑戰的項目」字樣），但人工複查時也要打開該章節實際讀一遍內容，不能只看有沒有這個標題
- [ ] 參考資料完整，逐條列出，不用「[8-30] 其餘略」這種區間省略；**每條引用必須是獨立文章、附真實可點擊 URL，不要把好幾篇不同文章合併成一個編號**（2330 案例 v1 版本犯過這個錯，8 個編號其實混了 20 幾篇文章，v2 改成逐篇編號後 verify_citations.py 的驗證才有意義）
- [ ] 若有取得現金流量表資料，**預設要做 DCF**，不要因為「資料看起來不全」就直接放棄——先查 FinMind 是否有 `TaiwanStockCashFlowsStatement` 這類 dataset，很多時候資料其實存在，只是需要多查一個 dataset
- [ ] 分析師共識目標價章節是否存在（見 data-researcher.md 的 Consensus 小節），這是 S1~S6 原始設計裡的缺口，不能省略
- [ ] 無佔位符（TBD、TODO、「內容過長省略」）
- [ ] **跨章節同一指標數值一致**：執行 `python3 ~/.claude/skills/equity-research-tw/scripts/check_number_consistency.py --report [path]`，逐一確認「高風險」清單（同一指標在相同期間出現不同數值）中每一項屬「口徑不同且報告內已明確區分」或「數字錯誤需修正」。**實測背景（8 家樣本 × 4 家 LLM 評審）**：此類錯誤佔正確性構面失分原因的 29%，且高度機械可偵測——鴻海 H1 EPS 正文寫 7.83 而官方為 7.84、營業利益率 3.72% 與 3.67% 並存；台達電摘要寫淨利年增 86.3% 而內文寫 EPS 年增 88.9% 未區分口徑；勤誠 2025 全年營收三處寫 210.01 億（實際 220.01 億）且該數字被 DCF 引用；川湖宣稱目標價可回推自 60/40 加權公式，實算 10,567 對報告所載 12,000
- [ ] **報告內所有「依 X% ＋ Y% 加權」「以 A 乘以 B 得出 C」這類可驗算的敘述，定稿前自行重算一次**，確認算得出宣稱的數字。川湖案例顯示：此類錯誤常在「回應紅隊挑戰時新增公式」的階段產生，而紅隊複核只跑一次、審查對象是初稿，無法攔截修改階段新引入的算術錯誤
- [ ] **多步驟公式（加權目標價、DCF、市值換算等）不能只用文字描述方法論，正文須寫出至少一行「數字代入＋等號＋結果」的算式，不能只寫「依FactSet共識權重60%＋可比乘數權重40%加權計算」這種純文字敘述而不帶實際數字**。原因：(1) 讀者若看不到實際代入的數字，無從自行覆核；(2) `check_number_consistency.py` 新增的公式覆算檢查（`check_arithmetic`）只能覆核「文字裡確實寫出數字算式」的部分，若正文只寫方法論文字、不帶數字，這個腳本形同虛設，無法幫忙抓錯。**已知失敗模式（2308 案例，台達電，2026-09）**：估值分析章節文字寫「以FY2025實際自由現金流52.75億元為基期」，但財務分析章節已明確算出FY2025自由現金流為527.5億元——DCF最終寫出的926/580/1,415元三個數字，其實是用527.5億元算出來的（重新代入驗算後確認），但正文敘述句本身寫錯成52.75億元，形成報告自相矛盾且無法被讀者依文字覆核；同一份報告的市值也在公司概況與估值分析兩處都寫成「4,740.5億元」，但依股本25.975億股×股價1,825元換算，正確值應為4.74兆元（47,404.5億元），同樣相差10倍且兩處重複同一錯誤——顯示「自行重算一次」這個步驟當時並未真正落實到市值與DCF基期這類「輸入值」本身，只驗證了公式本身的邏輯正確性。**具體要求**：DCF至少要在正文寫出「企業價值＋淨現金＝股權價值；股權價值÷股數＝每股價格」這個最終過渡算式並代入實際數字（不要求逐年折現過程全部攤開，但這個最後一步必須帶數字）；市值、EV等由「股本×股價」或類似乘法推得的數字，正文出現處旁邊要能讓讀者用同一句話裡的另外兩個數字自行乘出來，不能只給結論值
- [ ] 若上一項已依規定寫出數字算式，執行 `python3 ~/.claude/skills/equity-research-tw/scripts/check_number_consistency.py --report [path]`後，確認輸出最上方的「公式覆算檢查」區塊也是 PASS（無不吻合項目）——這是與「跨章節同一指標數值一致」不同的獨立檢查，前者比對「同一指標的不同數值」，後者比對「單一算式本身對不對」，兩者都要看
- [ ] 讀者導向正文（評等摘要～主要風險、資料缺口與限制）沒有夾雜「Red Team」「代理人交鋒」「Agent 3」「跨模組交叉檢驗」「S6模組初判」這類內部生成/複核過程用語。**已知失敗模式（2308 案例，台達電，2026-08）**：紅隊複核明明有真的執行、內容也扎實，S7 卻習慣性把「經Red Team複核後…」「【Red Team複核後更新】」這類標記直接留在估值分析、投資論點等正文段落交卷，讀起來像帶審閱註記的工作稿而非乾淨定稿——這類過程細節該移入「資料完整性與查證紀錄」章節，正文只呈現改寫後的分析結論（例如把「經Red Team複核後，本益成長法權重下修」改寫成「本益成長法之關鍵輸入EPS來源時效未確認，估值權重下修」）。**2026-09 更新**：「結論影響追蹤」子節原本是此項檢查的例外（因舊模板規定其措辭含「跨模組交叉檢驗」），現已同時做兩件事解除此例外——模板措辭改為中性用語、且該子節整段移入「資料完整性與查證紀錄」章節，因此讀者導向正文不再有任何合法出現這類用詞的位置，例外條款取消。`validate_equity_report.py` 已同步移除該豁免邏輯

可執行既有腳本輔助檢查：
```bash
python3 ~/.claude/skills/equity-research-tw/scripts/validate_equity_report.py --report [path]
python3 ~/.claude/skills/equity-research-tw/scripts/check_number_consistency.py --report [path]
python3 ~/.claude/skills/deep-research/scripts/verify_citations.py --report [path]
```
- `validate_equity_report.py` 是本 skill 專屬的驗證腳本（2330 案例後新增），檢查章節完整性（比對 `templates/final_report_template.md` 的實際結構，不是 deep-research 那套一般研究報告的章節）、佔位符、正文引用編號跟參考資料條目是否一一對應、每條參考資料是否都附真實 URL。**不要再用 deep-research 的 `validate_report.py`**——它的「Required Sections」是寫死給 Introduction／Main Analysis／Synthesis 那套用的，套在財報結構上一定 FAIL，是已知的誤判，2330 案例已經確認過這件事。
- `check_number_consistency.py`（2026-09 新增）掃描讀者導向正文（已自動排除同業比較、競爭地位、查證紀錄等會合理並列多個數字的章節），把同一指標出現多個不同數值的位置全部列出，並分成「高風險（同期間不同值）」與「待確認（期間不同）」兩級。它**不判斷哪個數字才對**——那需要外部查證；它只負責把候選位置攤開來給人逐一確認。實測 8 份報告每份高風險 0～6 項，屬可人工掃過的量。
- `verify_citations.py` 只認 `## 參考資料` 這個標題（不是 `## Bibliography` 或 `## Sources`），且每條引用都要附真實可存取的 URL、不能把多篇文章合併成一個編號——2330 v1 版本 8 個編號其實混了 20 幾篇文章，verify_citations.py 因此只能整批判定「無法驗證」；v2 改成逐篇獨立編號（13 條）後，12/13 通過（僅 FinMind API 因為是需要參數的端點，HEAD 請求回 405，屬預期例外）

## Step 4：交付 Markdown

品質檢查全部通過後，Markdown 檔案本身就是最終交付物，不需要再轉檔：
1. 輸出檔名：`{公司}_{代號}_equity_research_{YYYYMMDD}.md`
2. 存放位置：`outputs/{公司}_{代號}_{YYYYMMDD}/` 資料夾內
3. 完成後回報使用者檔案路徑＋一段 200-400 字的執行摘要，不在對話裡整篇貼出報告全文

**若使用者另外要求 Word (.docx) 版本**（例如單次需要，不是預設行為）：實測（2330 案例）發現 `anthropic-skills:docx` skill 預期環境已有 npm `docx` 套件與 LibreOffice(`soffice`)，但這台機器上兩者都不存在（`node -e "require('docx')"` 報 MODULE_NOT_FOUND；`soffice` 不在 PATH）。財報分析報告是純散文＋條列（S1~S6 已把表格資訊轉寫成散文，S7 不會有 markdown 表格），直接用系統既有的 `pandoc` 轉換即可，不需要 docx-js：
```bash
pandoc report.md -f markdown -t docx --toc --toc-depth=2 -o output.docx
```
不要額外傳 `-M title=...`（Markdown 裡已經有一個 `#` 標題，會重複出現兩次）。轉換後用 `python3 -c "import docx; ..."` 檢查段落數與標題階層、用 `unzip -t` 確認 zip 完整性——這台機器沒有 `soffice`，無法做「轉 PDF 截圖看畫面」的最終視覺驗證，這是已知缺口，交付時要如實告知使用者。
